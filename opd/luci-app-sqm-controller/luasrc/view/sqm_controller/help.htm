SQM 控制器运维手册

系统概览 页面导览 快速上手 队列后端 监控持久化 分类规则 策略中心 关键路径 常用命令 排障说明

系统概览

当前系统支持软件 HTB 多类队列和 IPQ807x NSS 硬件队列两种后端，并包含实时监控、持久化历史、分类打标、策略中心、自检及日志维护。 软件模式的下载方向依赖 ingress -> ifb0，上传方向直接在 WAN 接口整形；NSS 模式由 sqm-scripts-nss 接管基础带宽整形。

01

基础整形

根据 basic_config 里的接口、带宽、算法和队列后端生成软件队列，或桥接到 NSS 硬件队列。

作用：提供上传/下载方向的基础整形，并按硬件能力选择运行后端。
02

下载重定向

把 WAN ingress 流量重定向到 ifb0，让下载方向也能被 tc 分类和整形。

备注：没有 ifb0 或 ingress redirect，下载分类不会成立。
03

分类打标

当前版本主要依赖 classification 和 class_rule，通过端口规则写入 mark，再映射到类。

备注：这是“端口级粗分类”，不是厂商级应用识别。
04

策略中心

后台每分钟采集一次带宽、延迟、丢包和系统指标，并以 JSONL 持久化；网页提供实时值和长期窗口。

作用：页面关闭或路由器重启后，已采集的历史仍可读取。

页面导览

基础设置

配置接口、带宽、队列算法、队列后端、策略、监控目标和日志选项。

作用：强制 NSS 与当前硬件不兼容时会阻止保存并显示原因。
配置向导

按步骤写入基础配置并立即应用。

备注：适合首次部署。
状态监控

查看总体健康、TC 队列、ECN、分类链路、活动后端和策略任务。

作用：以队列和分类链路为准；没有常驻进程是正常设计。
实时监控

查看带宽、延迟、抖动、可用性和系统指标，支持 1 分钟至 24 小时窗口及 CSV 导出。

备注：后台每分钟持久化一次，页面每 3 秒补充当前实时值。
分类流量统计

查看默认/其他类、低时延类、流媒体类、批量下载类四类流量，支持切换下载/上传视角。

作用：同时看 tc 类速率、规则首次命中统计和链路诊断。
策略中心

执行一次策略、读取状态快照、预览最近记录、导出报告。

备注：当前策略相关操作和记录查看都集中在这一页。
系统日志

查看与筛选日志、按级别过滤、运行自检、轮转日志，并处理配置备份与恢复。

作用：日志是主视区，自检和备份恢复作为维护工具集中在侧栏和折叠区。
帮助文档

说明当前实现、配置顺序、命令和排障方式。

备注：文档内容只描述当前代码已实现的能力。

快速上手

  1. 先确认 WAN 接口和带宽 在“基础设置”或“配置向导”里填好实际 WAN 接口、上传/下载带宽、队列算法和队列后端。x86 建议使用“自动检测”或“软件模式”。
    作用：没有正确接口和带宽，后面的所有分类与策略都不可信。
  2. 启用服务并检查 qdisc 启用后先去“状态监控”确认 1: 和 2: root qdisc 是否存在。
    备注：看页面不如直接看 qdisc，排错更快。
  3. 应用分类器并检查 ifb0 应用分类器后确认 ifb0 上有下载类和下载 filters。
    作用：下载分类成立的前提是 ifb0、redirect 和 fw filter 全部就位。
  4. 查看分类流量统计 下载方向看 ifb0，上传方向看“接口”。规则命中表是首次命中统计，不是整条流量累计统计。
    备注：现代业务大量走 443，不可能只靠端口做到精确厂商识别。
  5. 进入策略中心 先点“执行一次策略”，再看当前模式、判定原因、动作数量和最近记录预览。
    作用：验证策略逻辑和导出能力是否正常。
  6. 最后再看日志 失败时先用日志筛选和“运行自检”，再决定是配置问题、环境问题还是规则覆盖率不足。
    备注：日志比页面告警更接近真实故障点。

建议

首次调试时先用一条明确的 HTTP 或 HTTPS 受控流量验证分类链路，不要直接混杂浏览器流量。

注意

当前默认规则属于端口级保守覆盖。国内视频和音乐业务主要仍由 tcp/udp 443 规则承接。

排障思路

先确认链路是否通，再讨论规则是否覆盖。如果链路没通，继续加规则没有意义。

队列后端

队列后端决定基础整形由软件 TC 还是 Qualcomm NSS 硬件卸载执行。

自动检测IPQ807x 且 NSS 模块、nss-zk.qos 和 sqm-scripts 均可用时选择 NSS，其余设备使用软件模式。
软件模式使用 HTB 多类队列、ifb0、nft mark 和 TC fw filter，完整支持分类流量统计与策略中心。
NSS 硬件模式仅适用于具备 Qualcomm NSS 的 IPQ807x 设备，提供基础带宽整形和监控，不支持本项目的软件多类分类链路。

x86 设备

x86 不具备 IPQ807x NSS 硬件。强制选择 NSS 时设置页会阻止保存，并显示具体检测失败原因；请选择“自动检测”或“软件模式”。

后端切换遵循“停止旧后端、清理旧队列、启动新后端”；清理失败时不会继续叠加另一套队列。

监控持久化

监控历史由后台任务采集，不依赖浏览器页面是否打开。

实时刷新页面每 3 秒读取当前样本，用于显示即时带宽、延迟、抖动和可用性。
后台持久化Cron 每分钟执行一次 main.py --monitor，追加一条 JSONL 样本。
历史窗口支持 1 分钟、5 分钟、1 小时、6 小时和 24 小时，可导出当前窗口 CSV。
保留容量最多保留 2880 条分钟样本，约 48 小时；超出阈值后压缩为最近记录。
Ping 配置目标、包数量和超时从 UCI 读取，默认目标为 223.5.5.5，并进行格式校验。
历史文件：/etc/sqm_controller/monitor_history.jsonl。旧 JSON 数组会在首次追加前迁移为 JSONL。

分类规则

当前版本的分类器以 proto + dport + sport 为主，先在防火墙侧打 mark，再由 tc 把 mark 映射到类。

默认/其他类 对应 other，是合法的默认分类，未命中的流量会先落到这里。
低时延类（游戏/会议） 对应 gaming，面向低延迟业务，当前默认规则主要覆盖部分常见游戏 UDP 端口。
流媒体类 对应 streaming，面向流媒体业务，当前默认规则覆盖 443、1935、554、8554、1755 等保守媒体端口。
批量下载类 对应 bulk，面向批量下载和传输，当前默认规则覆盖 80、BT 常见端口段、51413 等。
作用：通过 mark 把不同业务导入不同 tc 类。
备注：规则命中统计页面显示的是“规则首次命中”，因为后续同连接的流量主要依赖 conntrack mark 继承，不会持续累加到分类规则计数器。
低时延类（gaming）：3478, 3659, 3074, 3479-3480, 27000-27200 流媒体类（streaming）：443, 1935, 554, 8554, 1755 批量下载类（bulk）：80, 6881-6999, 51413

策略中心

策略中心用于执行策略判断、查看状态快照、预览最近记录，并支持 JSON/CSV 导出。

执行一次策略 调用 policy_once，立即运行一次策略判断并返回结果。
状态快照 读取 /tmp/sqm_decision_state.json，展示当前模式和最近调整时间。
最近记录预览 读取报告导出接口中的最近记录，方便快速判断策略是否真正生效。
导出 JSON/CSV 把策略记录导出为结构化数据，方便留档、分析或答辩展示。
作用：把策略判断、状态查看和记录导出集中到同一个页面。
备注：兼容访问历史书签地址时，也会直接跳到策略中心。

关键路径

/etc/config/sqm_controller 主配置文件，包含基础配置、分类规则和策略配置。
/usr/lib/sqm-controller/main.py 主 CLI 入口，LuCI 绝大多数按钮最终都会调用它。
/var/log/sqm_controller.log 运行日志，排查 enable、classifier、policy 失败时优先查看。
/var/log/sqm_policy.jsonl 策略记录日志，导出报告和预览最近记录都依赖它。
/etc/sqm_controller/monitor_history.jsonl 监控持久化历史，每分钟追加一条，路由器重启后继续保留。
/usr/lib/sqm-controller/nss_detect.py 检测设备型号、NSS 内核模块、nss-zk.qos 和 sqm-scripts 运行时，并解析实际队列后端。
/etc/config/sqm NSS 模式使用的 sqm-scripts 配置；软件模式会停止并清理本插件管理的 NSS section。
/tmp/sqm_decision_state.json 策略当前状态快照。模拟运行不会写入，只有安全下发流程成功后才会更新。
/tmp/sqm_classifier_rule_state.json 分类规则窗口状态缓存，用于计算首次命中的窗口增量。
作用：快速定位配置、日志、快照和临时状态文件。

常用命令

下面这些命令覆盖配置检查、运行状态、分类链路、策略中心和日志排查。每条命令都标明“作用”和“备注”，方便直接照着执行。

基础运行

/etc/init.d/sqm-controller start 作用：启动 SQM 服务、应用当前整形配置并同步策略与监控 Cron。
备注：统一服务启动入口，Web、CLI 和开机自启都应走这条路径。
/etc/init.d/sqm-controller stop 作用：停止 SQM 服务并清理软件 TC 或本插件管理的 NSS 运行态。
备注：同时移除策略和监控定时任务。
/etc/init.d/sqm-controller restart 作用：重启 SQM 服务并重新应用当前配置。
备注：修改带宽、队列算法或分类规则后优先使用这一条。
python3 /usr/lib/sqm-controller/main.py --status-json 作用：查看当前 service、qdisc 和 ECN 状态。
备注：这是 LuCI 状态页底层使用的状态接口之一。
uci show sqm_controller 作用：查看当前 UCI 配置是否已经写入。
备注：确认配置保存成功，比只看前端输入框更可靠。
python3 /usr/lib/sqm-controller/nss_detect.py auto 作用：检测 NSS 可用性并显示自动模式实际选择的后端。
备注：x86 正常结果应为 resolved_backend=software。
python3 /usr/lib/sqm-controller/nss_detect.py nss 作用：检查强制 NSS 是否可用。
备注：不可用时会返回 error 和具体原因。

实时监控与持久化

python3 /usr/lib/sqm-controller/main.py --monitor 作用：采集当前监控样本并追加到持久化历史。
备注：后台 Cron 每分钟执行一次。
python3 /usr/lib/sqm-controller/main.py --monitor-history --window 24h 作用：读取最近 24 小时历史并附带当前样本。
备注：查询本身不会写入历史文件。
grep sqm-controller-monitor /etc/crontabs/root 作用：确认后台监控任务已安装。
备注：服务启用时应存在，服务停止后应移除。
wc -l /etc/sqm_controller/monitor_history.jsonl 作用：查看已持久化的样本数量。
备注：服务运行时通常每分钟增加一条。

分类器与统计

python3 /usr/lib/sqm-controller/main.py --apply-classifier 作用：重新生成防火墙分类规则和 tc 分类映射。
备注：每次修改 classification 或 class_rule 后都应执行一次。
python3 /usr/lib/sqm-controller/main.py --clear-classifier 作用：清理分类器相关的防火墙规则和 tc 过滤器。
备注：分类链路异常时，可先清再重新应用。
python3 /usr/lib/sqm-controller/main.py --get-class-stats --dev ifb0 作用：查看下载方向的基础分类统计。
备注：只关注下载方向时，先看它是否有类速率变化。
python3 /usr/lib/sqm-controller/main.py --get-classifier-state --dev ifb0 作用：查看下载方向完整聚合状态。
备注：包含 summary、categories、rules、pipeline 和 diagnostics。
python3 /usr/lib/sqm-controller/main.py --get-classifier-state --dev iface 作用：查看上传方向完整聚合状态。
备注：页面里的“接口（上传）”就是这个视角。

tc / ifb0 / nft 排查

tc qdisc show dev eth1 作用：检查上传方向 root qdisc 是否已挂上。
备注：正常应能看到 1: root。
tc qdisc show dev ifb0 作用：检查下载方向 qdisc 是否已挂到 ifb0。
备注：正常应能看到 2: root。
tc class show dev ifb0 作用：查看下载类是否已经创建。
备注：应能看到 2:20 / 2:21 / 2:22 / 2:23。
tc filter show dev eth1 parent ffff: 作用：检查 ingress redirect 和 mark restore 链路。
备注：当前环境正常应出现 connmark 和 mirred redirect dev ifb0。
tc filter show dev ifb0 parent 2: 作用：检查下载方向 fw filter 是否映射到类。
备注：正常应看到 2:21 / 2:22 / 2:23 对应的 filter。
nft list chain inet sqm_fw sqm_classify 作用：查看当前 nft 分类规则和命中计数。
备注：这是判断规则是否实际命中的核心命令。

策略中心

策略模式 可选：智能自动、均衡模式、游戏模式、直播模式、会议模式、下载模式。
备注：直播、会议、下载只是用户场景名，底层仍映射到已有流媒体、游戏、批量队列。
python3 /usr/lib/sqm-controller/main.py --policy-once 作用：立即执行一次策略评估。
备注：只写策略日志，不自动下发 tc 队列变更。
python3 /usr/lib/sqm-controller/main.py --export-report --format json 作用：导出策略记录 JSON。
备注：适合做结构化分析或在浏览器中直接查看。
python3 /usr/lib/sqm-controller/main.py --export-report --format csv 作用：导出策略记录 CSV。
备注：适合导入表格工具或答辩材料。
cat /tmp/sqm_decision_state.json 作用：查看当前策略状态快照。
备注：dry-run 评估不会写入这个状态文件。
tail -n 20 /var/log/sqm_policy.jsonl 作用：查看最近策略记录。
备注：比页面预览更原始，适合确认导出内容是否正常。

日志与界面

tail -n 100 /var/log/sqm_controller.log 作用：查看应用日志的最近 100 行。
备注：排查后端异常时优先看它。
logread | grep -i sqm 作用：从系统日志中筛 SQM 相关消息。
备注：适合快速确认服务是否报错或重启。
logread | grep -E 'classifier|policy|ifb0|connmark' 作用：聚焦分类器、策略和下载链路相关日志。
备注：链路问题一般都能在这里看到关键词。
/etc/init.d/uhttpd restart 作用：重启 LuCI Web 服务。
备注：页面改动或缓存异常时再用，不是优先排障手段。

排障说明

NSS 是 Qualcomm IPQ807x 平台的硬件网络子系统，并不是通用的 x86 加速方式。设置页会运行 NSS 检测；型号、模块或脚本任一条件不满足时，强制 NSS 会被字段校验阻止。

x86 请选择“自动检测”或“软件模式”。自动检测在 x86 上解析为 software，并保留分类流量统计和策略中心能力。

先检查 /etc/crontabs/root 是否存在 sqm-controller-monitor。后台任务缺失时，页面仍能每 3 秒显示当前样本，但这些浏览器内存数据不能代替持久化历史。

服务启用后，历史文件应约每分钟增加一行。旧版本没有后台采样，因此升级前缺失的历史无法补录。

正常。SQM Controller 通过一次性命令应用 TC、nft 和 Cron，不要求主程序长期驻留。运行是否正常应以 TC 队列、分类链路和活动后端为准。

状态页总体健康显示“队列与分类链路均已生效”时，无常驻进程不是故障。

先不要把“默认/其他类占比高”直接当成故障。默认/其他类是合法分类，常见网页、工具、企业服务、遥测和通用 CDN 都可能落到这里。只有在“状态监控”显示链路不完整，或者“分类流量统计”里诊断明确提示防火墙、标记恢复、tc 队列缺失时，才优先按链路故障处理。

排障顺序：先看“状态监控”的运行方式和 TC 状态，再看“分类流量统计”的链路诊断，最后再决定是否需要补规则。

因为当前表格统计的是“规则首次命中”。同连接后续流量大多继承 conntrack mark，不会继续累加到分类规则计数器。

真正的持续吞吐请看四类流量卡片和 tc 类统计；规则表更适合判断“规则有没有开始生效”。

域名规则页里的“活跃规则数”和“活跃 IP 数”表示 DNS 缓存已经建立、并且有规则覆盖到这些 IP。它们主要用于生成动态分类依据，不等同于页面里每秒都会上涨的流量计数。只要活跃规则数和活跃 IP 数不是 0，说明 DNS 识别链路已经在工作。

如果“活跃规则数”长期为 0，再去查 dnsmasq 日志输入、域名规则覆盖和未分类域名导出；不要只盯某一个命中数字。

这是当前默认设计。定时任务使用的是 --policy-once，系统只做策略评估、记录和展示，不自动修改 tc 队列。这样更适合先验证分类质量、拥塞判断和分配计划是否合理。

看到“模拟运行 / 队列未下发”并不表示策略模块失效，而是当前仍处于只读验证阶段。

优先看这三处：一是“状态监控”里的运行方式、TC 状态和分类链路；二是“分类流量统计”里的诊断结果；三是“系统日志”里的最近日志。页面主要做汇总展示，真正的故障原因通常会先出现在状态页和日志里。

如果刚上传过页面文件，别忘了清 LuCI 缓存并重启 uhttpd，否则浏览器可能还在看旧模板。
